# Distributor: распределитель энергии и руды клана

`Distributor` (`IDistributor` = 0x304, класс в `Behavior.dll`, создаётся `CreateDistributor` 0x1001A840, размер 0x4C) - у каждого клана один
распределитель. Он делит между зданиями клана энергию и руду; логирует каждый шаг под названием «Distribution step of clan ...». Скрипты ИИ читают его
состояние: `GetDistributorSurplus`, `IsDistributorFlagSet` ([ScrLib](../ScrLib/README.md)). Строки отладки в `DistributeStep` называют его «Resource
Distributor».

## Данные

Запись `DistributorEntry` (28 байт, массив `entries` с `+0x1C`):

| Смещение | Поле | Смысл |
|:--:|---|---|
| 0x00 | `logic_id` | логический идентификатор здания (`FindBehaviourFromLogicID`) |
| 0x04 | `share` | доля (0..1) ресурсов клана, отведённая зданию; сумма долей не больше 1 |
| 0x08 | `is_locked` | ненулевое - доля задана явно и при пересчёте других не меняется |
| 0x0C / 0x10 | `power_given` / `power_received` | отдано и получено энергии на последнем шаге |
| 0x14 / 0x18 | `ore_given` / `ore_received` | то же по руде |

Итоги шага в самом распределителе: `+0x30` `power_available`, `+0x34` `ore_available`, `+0x38` `ore_in_buffer`, `+0x3C` `power_usage`, `+0x40`
`ore_usage`; `+0x0C` - индекс клана, `+0x10` - время прошлого шага.

## Управление долями

| Метод | Адрес | Что делает |
|---|---|---|
| `SetShare(id, share, locked)` | 0x1001B3B0 | задаёт долю (не меньше 0 и так, чтобы сумма заблокированных не превысила 1), добавляет запись, `locked == -1` - не менять признак |
| `ResetShare(id)` | 0x1001B4D0 | доля = 1 / число записей |
| `ResetAllShares` | 0x1001B660 | всем 1 / N, блокировка снимается |
| `RenormalizeShares(id)` | 0x1001B6A0 | остальные незаблокированные записи масштабируются так, чтобы сумма была 1 |
| `RemoveEntry(id)` | 0x1001B600 | удаляет запись и пересчитывает остальные |
| `Tick` | 0x1001B7C0 | по игровому времени вызывает `DistributeStep(dt)` |

## Шаг распределения (`DistributeStep`, 0x1001A980)

1. Для каждой записи берётся здание. Тип определяется логическим типом класса из `.dat` ([CpDatLib](../CpDatLib/README.md)): **источники энергии** -
   `Generator` 0x80000002 и бункеры `BunkerSmall/Medium/Large` 0x80010000/0x80020000/0x80040000 (в логе «Generator can give»: свойство `0x1005` × dt);
   **шахты и склады** `Mine` 0x80000004 и `Storage` 0x80000008 работают с рудой (свойство `0x1002`, ресурс `0x2000100`); все остальные - потребители
   («Non Generator want»: разница до максимума свойства `0x72`).
2. Суммируются доступная энергия и руда, запрос по долям (взвешенный по `share`) и полный запрос.
3. Коэффициенты (лог `fPowerA/B/Take`, `fOreA/B/Take`): если взвешенный запрос меньше предложения - приоритетные получают всё (A = 1), остальные - остаток
   пропорционально (B); иначе приоритетные получают долю предложения (A = S / запрос), остальные ничего. `Take` - доля, которую забирают у источников.
4. Второй проход начисляет значения зданиям («Non Generator received», «Mine Storage gave», «Non Mine Storage received») и обновляет итоги.

## Не выяснено

- точная формула коэффициентов в декомпиляции перепутана (переменные переиспользуются): знаки и роль `share` в потреблении не подтверждены данными;
- значения свойств `0x71`, `0x72`, `0x1002`, `0x1005` приведены по использованию, названия не подтверждены;
- где в интерфейсе игрока задаются доли (UI в `iron3d`/`Wizard` не найден).
